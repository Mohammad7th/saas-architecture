# معماری فرانت‌اند چندمحصولی

این پروژه یک مونوریپوی فرانت‌اند با دو محصول مستقل React است: **Admin** برای مدیریت کاربران و **Profile** برای مشاهده و ویرایش حساب کاربر واردشده. تمرکز پروژه بر تفکیک مسئولیت‌ها، اشتراک کد و امکان توسعه توسط چند تیم است.

## نصب و اجرا

پیش‌نیازها: Node.js نسخه‌ی 22.12 یا بالاتر و pnpm نسخه‌ی 12.10.1. نسخه‌ی pnpm در فیلد `packageManager` مشخص شده است.

```sh
pnpm install --frozen-lockfile
```

API را در یک ترمینال اجرا کنید:

```sh
pnpm dev:api
```

در ترمینالی دیگر، فقط اپ موردنیاز را اجرا کنید:

```sh
pnpm dev:admin
# یا
pnpm dev:profile
```

برای اجرای هم‌زمان هر دو فرانت، از `pnpm dev` استفاده کنید. این دستور API را اجرا نمی‌کند.

| بخش      | آدرس                           |
| -------- | ------------------------------ |
| Admin    | http://localhost:3000/admin/   |
| Profile  | http://localhost:3001/profile/ |
| Mock API | http://localhost:4000/api      |

هر فرانت درخواست‌های `/api` را به API محلی proxy می‌کند. اجرای Admin به اجرای Profile وابسته نیست و برعکس؛ هر تیم فقط API و اپ خودش را اجرا می‌کند. اگر پورت فرانت اشغال باشد، اجرا با خطا متوقف می‌شود و پورت خودکار تغییر نمی‌کند.

برای اشتراک cookie ورود بین دو اپ، هر دو را با نام میزبان `localhost` باز کنید. برای رفتن از یک محصول به محصول دیگر، اپ مقصد هم باید اجرا شده باشد.

| حساب | ایمیل              | رمز عبور |
| ---- | ------------------ | -------- |
| مدیر | admin@example.com  | demo1234 |
| عضو  | member@example.com | demo1234 |

## قابلیت‌ها

- **Admin:** ورود و خروج، مسیرهای محافظت‌شده، جست‌وجو و صفحه‌بندی کاربران، مشاهده‌ی جزئیات و ویرایش اطلاعات و نقش کاربر.
- **Profile:** ورود و خروج، مشاهده‌ی حساب فعلی و ویرایش اطلاعات پروفایل.
- **حالت‌های رابط کاربری:** بارگذاری، داده‌ی خالی، اعتبارسنجی، موفقیت، خطا و تلاش مجدد.

عضو عادی به API مدیریت کاربران دسترسی ندارد و نمی‌تواند از طریق ویرایش پروفایل نقش خود را تغییر دهد. مدیر نیز نمی‌تواند نقش مدیریتی حساب خودش را حذف کند.

## معماری و ساختار پروژه

پروژه یک **مونوریپو با pnpm Workspaces و Nx** است. داخل هر اپ، کد بر اساس مسئولیت به لایه‌های صفحه، کامپوننت و hook تقسیم شده و در هر لایه بر اساس حوزه‌ای مثل کاربران دسته‌بندی می‌شود.

```text
apps/
  admin/src/
    app/
      App.tsx
      routes.tsx
      RequireAuth.tsx
      RequireAdmin.tsx
    components/layout/
      AppLayout.tsx
    pages/users/
    components/users/
    hooks/auth/
    hooks/users/
  profile/src/
    app/
    pages/
    components/
    hooks/
packages/
  api-client/src/
    http.ts
    auth/
      auth.api.ts
      auth.schema.ts
    users/
      users.api.ts
      users.schema.ts
  ui/
tools/
  mock-api/
```

هر محصول entry point، router، QueryClient و خروجی build مستقل دارد. جابه‌جایی بین محصولات با لینک و بارگذاری صفحه انجام می‌شود. پکیج‌های مشترک هنگام build مصرف می‌شوند. برای نیاز فعلی، ترکیب محصولات در زمان اجرا با Micro Frontend یا Module Federation پیچیدگی ضروری‌ای ایجاد نمی‌کند؛ هر اپ با همین ساختار هم می‌تواند خروجی استقرار جدا داشته باشد.

### مسئولیت بخش‌ها

| بخش              | مسئولیت                                                                |
| ---------------- | ---------------------------------------------------------------------- |
| `app`            | اتصال اجزای اپ، تعریف مسیرها و محافظت از دسترسی                        |
| `pages`          | ترکیب اجزای صفحه و نمایش وضعیت دریافت داده                             |
| `components`     | نمایش اطلاعات و فرم‌های مخصوص محصول                                    |
| `hooks`          | مدیریت queryها، کش، ارسال فرم و ارتباط با مسیرها                       |
| `api-client`     | ارسال HTTP، مدیریت خطای API، توابع هر حوزه، schemaها و typeهای قرارداد |
| `ui`             | theme مبتنی بر MUI و اجزای نمایشی مشترک                                |
| `tools/mock-api` | شبیه‌سازی محلی API برای توسعه                                          |

`api-client` به React، TanStack Query یا router وابسته نیست. schemaها و typeهای هر حوزه کنار توابع HTTP همان حوزه قرار دارند؛ Zod پاسخ‌های دریافتی را در زمان اجرا بررسی می‌کند.

query keyها و hookهای هر محصول داخل اپ قرار دارند. adapterهای کوچک ورود و خروج نیز محلی‌اند تا سیاست کش هر محصول مستقل بماند؛ درخواست‌های HTTP آن‌ها مشترک است. برای هر موجودیت، پکیج مستقلی ایجاد نشده است.

فرم Admin و Profile جدا هستند، چون قابلیت ویرایش نقش فقط متعلق به Admin است. منطق ارسال و اعتبارسنجی فرم در hookها قرار دارد؛ فایل‌های TSX نمایش وضعیت و اتصال رویدادها را انجام می‌دهند. تصمیم‌های کوچک و صرفاً نمایشی داخل کامپوننت باقی می‌مانند.

### محل hookها و کامپوننت‌های مشترک

مشترک‌بودن یک قطعه کد لزوماً به معنای ساخت پکیج یا پوشه‌ی `shared` نیست؛ ابتدا محدوده‌ی استفاده‌ی آن مشخص می‌شود. در این ساختار، پوشه‌های `hooks` و `components` متعلق به کل اپ هستند و فقط به یک صفحه محدود نیستند.

| محدوده‌ی استفاده                                   | محل قرارگیری                                      | مثال                                                                                                                 |
| -------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| چند صفحه در یک حوزه‌ی همان اپ                      | پوشه‌ی همان حوزه در `hooks` یا `components`       | `apps/admin/src/hooks/users/useUsers.ts` یا `apps/admin/src/components/users/UserTable.tsx`                          |
| چند حوزه در همان اپ، بدون وابستگی به یک حوزه‌ی خاص | پوشه‌ی `common` در لایه‌ی مربوط                   | `apps/admin/src/hooks/common/useDebouncedValue.ts` یا `apps/admin/src/components/common/ConfirmDialog.tsx`           |
| چند اپ، برای اجزای نمایشی عمومی                    | پکیج `packages/ui`                                | کامپوننت مشترک نمایش خطا یا loading                                                                                  |
| چند اپ، برای hookها                                | بر اساس مسئولیت و وابستگی hook تصمیم گرفته می‌شود | hook صرفاً نمایشی می‌تواند کنار اجزای مرتبط در `ui` قرار بگیرد؛ hook مربوط به query و کش فعلاً در اپ‌ها باقی می‌ماند |

مسیرهای `common` بالا مثالِ محل افزودن کد در آینده‌اند؛ تا زمانی که مصرف واقعی ندارند، پوشه‌ی خالی برای آن‌ها ایجاد نمی‌کنیم. اگر کامپوننتی مثل جدول کاربران در چند صفحه استفاده شود ولی همچنان مخصوص حوزه‌ی کاربران باشد، در `components/users` باقی می‌ماند و به `common` منتقل نمی‌شود.

پوشه‌ی جداگانه‌ی `src/shared` نداریم، چون در معماری لایه‌ای فعلی، نوع مسئولیت با `hooks` و `components` مشخص شده است. ساخت هم‌زمان `shared/hooks` در کنار `hooks/common` دو محل مبهم برای یک کاربرد ایجاد می‌کند؛ برای اشتراک داخل اپ فقط از مسیرهای همین جدول استفاده می‌کنیم.

hookهای مربوط به داده‌ی سرور نباید صرفاً به دلیل مشترک‌بودن وارد `ui` یا `api-client` شوند؛ `ui` نمایشی است و `api-client` به React وابسته نیست. اگر در آینده چند اپ واقعاً به یک سیاست query و کش مشترک نیاز داشته باشند، استخراج یک ماژول یا پکیج متناسب با همان مسئولیت بررسی می‌شود. وجود چند خط مشابه به‌تنهایی دلیل ساخت پکیج عمومی `shared` نیست.

### مرز وابستگی‌ها

اپ‌ها پکیج‌های مشترک را از خروجی عمومی آن‌ها مصرف می‌کنند. پکیج‌ها به اپ‌ها وابسته نیستند. `ui` مسئولیتی در احراز هویت، API یا مسیریابی ندارد و Mock API نیز هیچ وابستگی به پکیج‌های فرانت ندارد.

قانون `@nx/enforce-module-boundaries` در ESLint با tagهای پروژه‌ها، مرز وابستگی‌ها را کنترل می‌کند. import نسبی بین پروژه‌ها، وابستگی چرخه‌ای و مصرف وابستگی انتقالیِ اعلام‌نشده نیز بررسی می‌شوند. واردکردن مسیرهای داخلی و خصوصی پکیج‌ها مجاز نیست. دستور `pnpm check:boundaries` همان بررسی lint را اجرا می‌کند.

## دلیل انتخاب ابزارها

| ابزار                 | دلیل استفاده                                                             |
| --------------------- | ------------------------------------------------------------------------ |
| React و TypeScript    | ساخت رابط کاربری با اجزای مستقل و قراردادهای تایپ‌شده                    |
| Vite                  | اجرای توسعه و build مستقل هر اپ                                          |
| TanStack Query        | مدیریت داده‌ی سرور، کش و به‌روزرسانی پس از mutation                      |
| React Router          | تعریف مسیرها و رفتار مسیریابی در هر محصول                                |
| MUI                   | ساخت رابط کاربری یکدست با اجزای آماده                                    |
| React Hook Form و Zod | مدیریت فرم و اعتبارسنجی ورودی و قرارداد داده                             |
| pnpm Workspaces       | نصب وابستگی‌ها، lockfile مشترک و اتصال پکیج‌های محلی با `workspace:*`    |
| Nx                    | اجرای taskها، نمودار وابستگی، کش محلی و اعمال مرزهای معماری برای چند تیم |
| json-server           | API محلی و مستقل برای توسعه و اجرای نمونه                                |

تنظیمات TypeScript، ESLint و Prettier در ریشه مشترک‌اند. برای این تنظیمات پکیج‌های جدا ساخته نشده‌اند. استفاده از Nx به حساب ابری یا remote cache نیاز ندارد.

## مدیریت state و مسیرها

داده‌های سرور و کش در اختیار TanStack Query هستند. React Hook Form وضعیت فرم را نگه می‌دارد، جست‌وجو و شماره‌ی صفحه در URL قرار می‌گیرند و stateهای نمایشی محلی با React مدیریت می‌شوند. داده‌های سرور در یک global store موازی کپی نمی‌شوند.

پس از mutation، داده‌ی جزئیات به‌روزرسانی و queryهای مرتبط با لیست، پروفایل یا session در صورت نیاز نامعتبر می‌شوند. ورود و خروج، درخواست‌های قبلی را لغو و داده‌های کش مربوط به کاربر قبلی را پاک می‌کنند.

مسیرهای هر اپ در `src/app/routes.tsx` تعریف می‌شوند. `App.tsx` آن‌ها را با `useRoutes` متصل می‌کند و با `Suspense` حالت بارگذاری صفحه‌های lazy را نمایش می‌دهد. مسیر پایه در `BrowserRouter` برای Admin برابر `/admin` و برای Profile برابر `/profile` است.

`RequireAuth` ابتدا session را بررسی می‌کند: هنگام دریافت، loading و هنگام خطا، امکان تلاش مجدد نمایش داده می‌شود. کاربر بدون session به Login هدایت می‌شود و پس از ورود به مسیر درخواستی برمی‌گردد. در Admin، guard جداگانه‌ی `RequireAdmin` نقش مدیر را بررسی می‌کند. مسیرهای مجاز در `Outlet` نمایش داده می‌شوند. پاسخ `401` از query یا mutation محافظت‌شده، session را پاک می‌کند تا اپ به جریان ورود برگردد.

## Mock API

Mock در `tools/mock-api` با JavaScript و json-server نسخه‌ی 0.17.4 پیاده شده است. این بخش فقط ابزار توسعه است و ساختار پکیج‌های فرانت را تعیین نمی‌کند. اعتبارسنجی‌های مختصر خودش را دارد؛ در صورت تغییر قرارداد API، داده‌ها و اعتبارسنجی Mock هم باید هماهنگ شوند.

```text
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
GET  /api/users
GET  /api/users/:id
PATCH /api/users/:id
GET  /api/me
PATCH /api/me
```

routeهای سفارشی، اعتبارسنجی، صفحه‌بندی و کنترل دسترسی را انجام می‌دهند. router عمومی CRUD در دسترس نیست تا این بررسی‌ها دور زده نشوند. درخواست‌ها تأخیر ثابت ۲۵۰ میلی‌ثانیه دارند.

کدهای خطا شامل `401` برای session نامعتبر، `403` برای دسترسی ناکافی، `404` برای کاربر پیدا‌نشده، `409` برای ایمیل تکراری و `422` برای ورودی نامعتبر هستند.

ورود، cookie از نوع `HttpOnly` با `SameSite=Lax` و اعتبار یک ساعت ایجاد می‌کند. sessionها در حافظه‌ی API هستند؛ با راه‌اندازی مجدد API باید دوباره وارد شد. اطلاعات کاربر در هر درخواست محافظت‌شده از داده‌ی فعلی خوانده می‌شود. فرانت session را هنگام بازگشت تمرکز به صفحه و هر ۳۰ ثانیه بررسی می‌کند؛ همگام‌سازی لحظه‌ای کش بین تب‌ها وجود ندارد.

تغییرات کاربران در `tools/mock-api/data/db.json` ذخیره می‌شوند. این فایل در Git نادیده گرفته شده و در اولین اجرا به‌صورت خودکار ساخته می‌شود. برای بازنشانی، API را متوقف کنید، همین فایل را حذف کنید و دوباره API را اجرا کنید.

برای سازگاری با نسخه‌ی قبلی پروژه، bootstrap اپ worker قدیمی MSW را در صورت وجود حذف می‌کند؛ داده‌های قبلی localStorage به فایل JSON منتقل نمی‌شوند.

Mock فقط روی loopback اجرا می‌شود و برای محیط production در نظر گرفته نشده است. رمز مشترک حساب‌های نمونه، ذخیره‌سازی در یک فایل و session حافظه‌ای، محدودیت‌های این ابزار نمایشی هستند. محیط واقعی به بک‌اند با احراز هویت، ذخیره‌سازی و تنظیمات امنیتی مناسب نیاز دارد.

تنظیمات اختیاری محیط اجرا:

| متغیر              | کاربرد                                              |
| ------------------ | --------------------------------------------------- |
| `API_PORT`         | تغییر پورت API؛ پیش‌فرض `4000`                      |
| `API_DB_FILE`      | انتخاب مسیر دیگری برای فایل داده                    |
| `API_PROXY_TARGET` | مقصد proxy در Vite؛ پیش‌فرض `http://127.0.0.1:4000` |

اگر پورت API تغییر کند، مقصد proxy فرانت هم باید تغییر کند. این متغیرها را هنگام اجرای دستور در محیط shell تنظیم کنید.

## build و استقرار

```sh
pnpm build
pnpm preview:admin
pnpm preview:profile
```

برای preview هم API باید جدا اجرا شود. آدرس‌ها همان پورت‌های ۳۰۰۰ و ۳۰۰۱ هستند؛ dev و preview یک اپ نباید هم‌زمان روی همان پورت اجرا شوند.

خروجی build شامل پیاده‌سازی Mock نیست. در استقرار واقعی، خروجی `dist` هر اپ را زیر مسیر پایه‌ی خودش با fallback مناسب SPA ارائه کنید و `/api` را به بک‌اند واقعی متصل کنید. proxy توسعه و preview در Vite جایگزین وب‌سرور production نیست.

لینک بین محصولات در build به‌صورت پیش‌فرض نسبی است. برای میزبان‌های جدا، از جمله preview روی دو پورت، قبل از build مقدار `VITE_ADMIN_URL` و `VITE_PROFILE_URL` را تنظیم کنید. اگر مسیر پایه‌ی API متفاوت از `/api` است، `VITE_API_BASE_URL` را تغییر دهید. استقرار API روی origin دیگر به تنظیم CORS و cookie در بک‌اند هم نیاز دارد. نمونه‌ی تنظیمات در `.env.example` آمده است.

## کیفیت کد و بررسی پروژه

```sh
pnpm format
pnpm format:check
pnpm lint
pnpm lint:fix
pnpm check
```

`pnpm check` به‌ترتیب فرمت، lint و مرزهای Nx، typecheck و build هر دو فرانت را بررسی می‌کند.

Prettier از `.prettierrc.json` و `.prettierignore` در ریشه استفاده می‌کند. ESLint نیز با `eslint.config.mjs` قوانین JavaScript و TypeScript، React Hooks و مرزهای پکیج‌ها را اعمال می‌کند. `eslint-config-prettier` قوانین قالب‌بندی متداخل را غیرفعال می‌کند.

Husky پیش از commit، ابزار lint-staged را اجرا می‌کند: فایل‌های کدِ staged بررسی و فرمت می‌شوند و فایل‌های JSON، Markdown و قالب‌های پشتیبانی‌شده نیز فرمت می‌شوند. build کامل داخل hook اجرا نمی‌شود؛ پیش از ارسال Pull Request، دستور `pnpm check` را اجرا کنید.

در یک Git repository، نصب وابستگی‌ها با اجرای `prepare`، hookها را فعال می‌کند. اگر Git را بعداً راه‌اندازی کردید، `pnpm prepare` را اجرا کنید. این تنظیمات خودشان repository ایجاد نمی‌کنند.

### اجرای taskها با Nx

```sh
pnpm graph
pnpm exec nx build @workspace/admin
pnpm exec nx affected -t lint typecheck build --base=main
```

Nx پروژه‌ها را از `package.json` هر workspace شناسایی می‌کند. همه‌ی پروژه‌ها task مربوط به `lint` دارند؛ پروژه‌های TypeScript دارای `typecheck` هستند. فرانت‌ها taskهای `dev`، `build` و `preview` دارند و Mock API با task مستقل `serve` اجرا می‌شود.

پکیج‌های مشترک، سورس TypeScript را export می‌کنند و Vite هنگام build اپ مصرف‌کننده آن‌ها را پردازش می‌کند؛ به build جداگانه‌ی کتابخانه نیاز ندارند. ورودی کش build شامل سورس وابستگی‌ها، تنظیمات مشترک، فایل‌های محیطی ریشه و متغیرهای `VITE_API_BASE_URL`، `VITE_ADMIN_URL` و `VITE_PROFILE_URL` است. taskهای توسعه کش نمی‌شوند؛ کش محلی در `.nx/` ذخیره می‌شود.

دستور `affected` به تاریخچه‌ی Git و مرجع مقایسه‌ی معتبر نیاز دارد. تا قبل از آماده‌شدن تاریخچه، از `pnpm check` استفاده کنید.

## توسعه‌ی قابلیت‌ها و همکاری تیم‌ها

1. صفحه و مسیر جدید را در اپ مالک قابلیت اضافه کنید؛ مسیر در `src/app/routes.tsx` ثبت شود و کامپوننت‌ها و hookها در لایه‌ی مربوط، بر اساس حوزه دسته‌بندی شوند.
2. عملیات HTTP را در پوشه‌ی حوزه‌ی مربوط در `api-client` قرار دهید. query keyها و سیاست کش در hookهای اپ باقی بمانند. فقط در صورت نیاز مشخص به استفاده‌ی مشترک یا مالکیت مستقل، پکیج تازه ایجاد کنید.
3. schemaها و Mock را با قرارداد جدید هماهنگ و قواعد دسترسی و به‌روزرسانی کش را مشخص کنید.
4. از خروجی عمومی پکیج‌ها استفاده کنید، وابستگی‌ها را در `package.json` اعلام کنید و پیش از ادغام تغییرات، بررسی‌ها را اجرا کنید.
5. برای محصول جدید، اپی با router، providerها و build مستقل بسازید؛ پورت توسعه، proxy API و مسیر پایه‌ی استقرار را مشخص کنید.

هر تیم می‌تواند مالک یک محصول یا حوزه‌ی مشترک باشد. تغییر پکیج مشترک باید با بررسی اپ‌های مصرف‌کننده همراه شود. پکیج‌های تازه باید tagهای مناسب Nx و وابستگی‌های محلی با `workspace:*` داشته باشند. با رشد مخزن می‌توان از taskهای `affected` برای محدودکردن بررسی‌ها به بخش‌های تحت تأثیر استفاده کرد.

مدل‌های API و مدل‌های داخلی محصول زمانی جدا می‌شوند که شکل یا چرخه‌ی تغییر آن‌ها واقعاً متفاوت شود؛ برای CRUD فعلی، مدل‌ها و لایه‌های واسط تکراری ایجاد نشده‌اند.
